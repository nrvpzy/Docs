# 3. What Is OAuth2?

OAuth2 is an authorization framework.

Do not overcomplicate it.

OAuth2 is basically a standard way for one system to say:

> I trust this identity provider to issue access tokens. If a request comes with a valid token, I can allow access to protected APIs.

In your case:

- ADFS issues tokens.
- Microservices validate tokens.
- The frontend uses the token to call APIs.

---

# 4. What Is OIDC?

OIDC means **OpenID Connect**.

It is built on top of OAuth2.

OAuth2 mainly answers:

> Can this client access this API?

OIDC adds identity and answers:

> Who is the user?

OIDC gives an **ID token** containing user identity claims.

Examples of claims:

- username
- email
- name
- subject ID
- groups
- issuer
- expiry

So:

> OAuth2 gives access to APIs.  
> OIDC gives identity information about the logged-in user.

Conceptually:

> UI → Gateway → toolboxadfsbridge → ADFS

# 6.3 toolboxadfsbridge redirects to ADFS

The bridge starts the OAuth2 Authorization Code flow.

It redirects the browser to ADFS with information like:

- client ID
- redirect URI
- requested scopes
- state
- nonce
- response type = authorization code

You do not need to remember every parameter, but understand the meaning:

> “ADFS, please authenticate this user. When done, redirect back to this callback URL.”

---

# 6.4 ADFS authenticates the user

Now the user is on JLR SSO / ADFS.

ADFS does the real login.

It may check:

- corporate username/password
- MFA
- account enabled/disabled
- enterprise policies
- password expiry
- group membership
- conditional access rules

Your app does **not** see the password.

That is the key benefit.

The application says:

> I trust JLR SSO. If ADFS says this user is valid, I trust that identity.

---

# 6.5 If the user is already logged into SSO

If the user already logged into another JLR app using SSO, ADFS may not ask for credentials again.

It may silently authenticate the user and redirect back.

That is the “single sign-on” part.

The user logs in once and can access multiple internal apps.

---

# 6.6 ADFS redirects back to toolboxadfsbridge

After successful login, ADFS does not directly send the full app session to the frontend.

It sends an **authorization code** back to the bridge callback URL.

Think of the authorization code like a temporary receipt.

It says:

> This user authenticated successfully. Exchange this code for tokens.

---

# 6.7 toolboxadfsbridge exchanges code for tokens

The bridge sends the authorization code back to ADFS from the server side.

ADFS returns tokens:

- ID token
- access token
- possibly refresh token depending on configuration

This exchange is handled server-side by Spring Security OAuth2 client.

That is why the bridge has a controller method like:

> `toolBoxSSOHandler(OAuth2AuthorizedClient authorizedClient, OidcUser principal, HttpServletResponse response)`

The method receives:

- OAuth2 authorized client
- OIDC user principal
- response object for setting cookie / redirect

---

# 6.8 toolboxadfsbridge extracts user claims

After token exchange, the bridge has access to the authenticated OIDC principal.

It can extract claims like:

- user ID
- email
- display name
- subject
- groups
- other enterprise attributes

The project has:

- `UserAuthenticationController.getUser()`
- `UserAuthenticationController.getClaimsFromBean()`
- `UserService.getJlrUserDetails()`
- `UserService.getUserClaims()`

These are used to expose or transform authenticated user details.

The app’s internal user object is represented by something like:

> `JlrUser`

---

# 6.9 toolboxadfsbridge creates the application session

After ADFS login succeeds, the application needs to keep the user authenticated.

A common pattern here is:

> Put the JWT/access token into a secure cookie.

Your backend services have:

> `cookieTokenResolver()`

That strongly suggests the token is expected in a cookie.

So the bridge or auth layer sets a cookie in the browser.

Example conceptually:

> access token cookie = signed JWT from ADFS

The cookie may be configured with:

- HttpOnly
- Secure
- SameSite
- Path
- Expiry

---

# 6.10 Browser redirects back to UI

After cookie/session is established, the user is redirected back to Toolbox UI.

Now when the frontend checks session again, it succeeds.

The user can see the main application.

Usually the first screen might be:

- dashboard
- landing page
- order management page

# 8. Why Use toolboxadfsbridge?

A very common question:

> Why do we need a separate SSO bridge?

Because OAuth2/OIDC login involves redirects, token exchange, callback handling, and claim extraction.

You do not want every frontend route or every microservice to handle that.

The bridge centralizes:

- OAuth2 client configuration
- redirect to ADFS
- callback handling
- token exchange
- OIDC principal extraction
- cookie/session setup
- exposing user claims

In short:

> toolboxadfsbridge is the adapter between the Toolbox application and enterprise ADFS.

# 9. Why Not Directly Authenticate in the Frontend?

Because frontend apps are not safe places to handle secrets.

A browser app cannot safely store client secrets.

Also, enterprise authentication should be handled through approved SSO flows.

So instead of:

> frontend collects username/password

you do:

> frontend redirects to enterprise SSO

That is safer, compliant, and easier to maintain.

# 13. Why Cookie-Based Token?

There are two common ways to send JWTs from frontend to backend.

## Option 1: Authorization header

Frontend stores token and sends:

> Authorization: Bearer token

Usually token is stored in memory or localStorage.

Problem:

> If token is in localStorage, JavaScript can access it. If XSS happens, token can be stolen.

---

## Option 2: Secure cookie

Browser stores token in a cookie.

If cookie is HttpOnly:

> JavaScript cannot read it.

Browser sends it automatically with requests.

This is why cookie-based JWT is common for browser apps.

---

# 14. What Is `cookieTokenResolver()`?

Spring Resource Server normally expects tokens in this format:

> Authorization: Bearer token

But your architecture uses cookies.

So services need a way to say:

> Instead of only checking the Authorization header, also look inside this cookie and extract the JWT.

That is what `cookieTokenResolver()` does.

In simple words:

> It pulls the JWT out of the browser cookie so Spring Security can validate it.

# 15. What Happens Inside a Microservice When Request Arrives?

Let’s say the user calls:

1. Browser sends request with JWT cookie.
2. Gateway routes it to `mcp-vehicle-order`.
3. `mcp-vehicle-order` security filter intercepts request.
4. `cookieTokenResolver()` extracts token from cookie.
5. Spring Security validates token:
   - signature
   - issuer
   - expiry
   - audience
6. If invalid or expired:
   - request rejected with 401.
7. If valid:
   - token is converted into Spring Authentication.
8. `JwtConverter` maps claims into principal/authorities.
9. Controller is allowed to execute.
10. Business logic runs.

# 21. What Is RBAC?

RBAC means Role-Based Access Control.

The model is:

> Users get roles.  
> Roles get permissions.  
> Permissions allow actions.

Example:

> ORDER_MANAGER  
> SAP_REPORT_VIEWER

Permissions from those roles:

- VIEW_ORDER
- SAVE_ORDER
- MODIFY_ORDER
- RETURN_VEHICLE.PUT
- SAP_HANDOVER_LIST
- SAP_HANDOVER_REPORT

Now the UI and backend know what Alice can do.

This is an important nuance.

# 34. Full Architecture Flow in One Long Story

Here is the full story from browser open to protected API access.

User opens Toolbox UI.

The frontend checks whether there is an authenticated session. There is no valid cookie/session, so it shows the login page.

The user clicks Login with SSO.

The browser is redirected to `toolboxadfsbridge`, which is configured as the OAuth2 client. The bridge redirects the browser to ADFS with an OAuth2/OIDC authorization request.

ADFS authenticates the user using JLR enterprise identity. It may validate password, MFA, account state, and enterprise policies. If the user is already signed into SSO, ADFS may skip the login form and immediately proceed.

After successful authentication, ADFS redirects back to the bridge with an authorization code.

The bridge exchanges the authorization code for tokens. It receives the ID token and access token, extracts the OIDC user claims, builds application user context, sets the JWT/access token into a secure cookie, and redirects the browser back to the UI.

Now the frontend can load the protected application. It calls toolboxadmin to get the current user’s authorization codes. toolboxadmin uses the user ID to find assigned roles and then finds authorization codes assigned to those roles. These codes come from the permission catalog seeded from `AuthorizationList.json`.

The frontend stores those authorization codes and uses them to filter the sidebar, protect routes, and show or hide buttons. For example, a user with `VIEW_ORDER` can see order list, a user with `SAVE_ORDER` can create orders, and a user with `RETURN_VEHICLE.PUT` can return vehicles.

When the user performs an action, the browser sends the API request with the JWT cookie. The gateway routes the request to the correct service. The target microservice extracts the JWT from the cookie using `cookieTokenResolver`, validates it using OAuth2 Resource Server security, maps claims using `JwtConverter`, and only then executes the controller method.

This gives the platform enterprise SSO, token-based authentication, centralized RBAC, role-aware UI, and independently secured microservices.

>
> After login, the frontend called `toolboxadmin` to resolve the user’s application permissions. toolboxadmin owned the RBAC model: users mapped to roles, roles mapped to authorization codes, and the authorization catalog was seeded from `AuthorizationList.json`. These codes represented fine-grained permissions like `VIEW_ORDER`, `SAVE_ORDER`, `MODIFY_ORDER`, `RETURN_VEHICLE.PUT`, and `VIEW_ROLE_MANAGEMENT`.
>
> The UI used those codes for role-aware rendering — filtering sidebar items, guarding routes, and showing or hiding buttons. Every backend microservice was configured as an OAuth2 resource server. Requests carried the JWT cookie, services extracted the token using a cookie token resolver, validated it, converted claims with `JwtConverter`, and then processed the request. This meant ADFS handled who the user was, toolboxadmin handled what they could do, and each microservice independently protected its APIs.

# 36. Cross-Question Preparation

## Q1. Explain OAuth2 in your project.

OAuth2 was used as the token-based security framework. The user authenticated through ADFS, the app received access tokens, and those tokens were used to access protected microservices. Each microservice validated the token before serving the API.

---

## Q2. Explain OIDC in your project.

OIDC was used on top of OAuth2 to get user identity. It gave us ID token and user claims such as username, email, and subject. The bridge used the OIDC principal to build the application user context.

---

## Q3. What was the OAuth2 client?

`toolboxadfsbridge` was the OAuth2 client. It initiated the login flow, redirected users to ADFS, handled the callback, exchanged the authorization code for tokens, and extracted user claims.

---

## Q4. What were the resource servers?

The protected backend microservices were resource servers. For example, `mcp-vehicle-order`, `toolboxadmin`, employee service, finance service, and vehicle-data service. They validated JWTs on incoming requests.

---

## Q5. What was ADFS?

ADFS was the enterprise identity provider. It authenticated users using JLR corporate identity and issued OIDC/OAuth2 tokens.

---

## Q6. Why not use username/password login?

Because this was an enterprise application. We wanted centralized authentication, MFA, corporate password policies, and centralized user lifecycle management. With ADFS, our application never handled user passwords.

---

## Q7. Why not Keycloak?

Keycloak could support OAuth2/OIDC, but ADFS was already JLR’s enterprise identity provider integrated with corporate directory and security policies. Using ADFS avoided introducing another identity system.

---

## Q8. What did the user get after successful login?

The user got an authenticated application session backed by tokens from ADFS. The access token/JWT was stored in a secure cookie and sent with API requests.

---

## Q9. What is the difference between access token and ID token?

The ID token describes the user identity. The access token is used to access protected APIs.

---

## Q10. What is JWT?

JWT is a signed token containing claims. Services can validate the signature and trust the claims if the token came from the configured issuer and is not expired.

---

## Q11. Why use cookies for JWT?

Cookies work naturally in browser apps. If configured as HttpOnly and Secure, they reduce token theft risk from JavaScript. The browser sends them automatically with API requests.

---

## Q12. What is the risk of cookie JWT?

CSRF is the main risk because cookies are sent automatically. Mitigations include SameSite cookies, secure CORS, CSRF tokens, and Origin/Referer checks.

---

## Q13. What is `cookieTokenResolver`?

It extracts the JWT from a cookie so Spring Security Resource Server can validate it. Normally Resource Server expects Authorization header, but this app supported cookie-based tokens.

---

## Q14. What is `JwtConverter`?

It converts a validated JWT into a Spring Security authentication object, mapping claims into principal and authorities.

---

## Q15. What is RBAC?

RBAC means users get roles, roles get permissions, and permissions determine what actions the user can perform.

---

## Q16. How did RBAC work here?

toolboxadmin managed users, roles, and authorization codes. After login, the UI fetched the user’s authorization codes and used them to filter pages and actions. Roles were mapped to permissions like `VIEW_ORDER`, `SAVE_ORDER`, and `RETURN_VEHICLE.PUT`.

---

## Q17. What is AuthorizationList.json?

It is the master permission catalog. It defines all authorization codes supported by the application. toolboxadmin loads these codes and lets roles be assigned from them.

---

## Q18. Why use fine-grained authorization codes?

Fine-grained permissions support least privilege. Instead of giving broad admin access, we can allow specific actions like view order, modify order, return vehicle, or generate SAP report.

---

## Q19. Is toolboxadmin called for every request?

Not necessarily synchronously for every request. It is the source of truth for RBAC. The UI typically fetches permissions after login and uses them for rendering. Backend services validate JWT locally and can enforce permission checks using cached or mapped permissions.

---

## Q20. Why not put all permissions in JWT?

If permissions are in JWT, permission changes do not take effect until token refresh. Keeping RBAC in toolboxadmin allows more flexible permission management. A hybrid approach can also be used.

---

## Q21. How does the UI use permissions?

The UI maps authorization codes to routes and buttons. If the user lacks a code, the route or button is hidden or blocked.

---

## Q22. Is hiding buttons enough?

No. It improves UX but is not sufficient security. Backend APIs must validate authentication and enforce authorization because users can call APIs directly.

---

## Q23. Why secure every microservice separately?

Defense in depth. Even if the gateway is bypassed or misconfigured, each service still rejects unauthenticated requests.

---

## Q24. What happens when token expires?

The service returns 401. The frontend clears auth state and redirects to login or refreshes the token if refresh flow exists.

---

## Q25. What happens when user lacks permission?

The user should get 403 Forbidden, or the UI should prevent the action from being visible. 401 means not logged in; 403 means logged in but not allowed.

---

Memorize this:

> ADFS authenticated the user, toolboxadfsbridge converted the SSO result into an application JWT session, toolboxadmin resolved fine-grained permissions, the UI rendered only authorized routes/actions, and every microservice validated the JWT before processing requests.

# 38. The “I Really Understand This” Version

If you want to sound senior:

> The key design decision was separating identity, session, and authorization. Identity came from ADFS through OIDC. Session continuity was handled through JWT cookies. API authentication was enforced independently by each resource server. Application authorization was centralized in toolboxadmin through role-to-permission mappings. This avoided password handling in the app, avoided duplicating RBAC logic across services, and gave us fine-grained least-privilege access across the platform.

# 40. Final Simplified Story

Here is the simplest possible version:

> The user does not log into our app directly. They log into JLR SSO through ADFS. ADFS proves who they are and gives us tokens. Our SSO bridge receives those tokens, extracts user info, and stores the access token as a secure cookie. The frontend then asks toolboxadmin what this user is allowed to do. toolboxadmin returns authorization codes based on the user’s roles. The UI uses those codes to show only allowed pages and actions. Whenever the UI calls a backend service, the browser sends the JWT cookie, and the service validates it before running the API. That is how we secured multiple microservices with enterprise SSO and centralized RBAC.
