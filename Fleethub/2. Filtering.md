# 9. What `FiltrationSpecificationUtil` Does

This is one of the key classes.

Important methods:

```text
createSpecification(List<FilterCriteria> filterCriteriaList, Boolean andClause)

getPredicate(FilterCriteria criteria, CriteriaBuilder cb, Root<T> root)

getValueAsPerDataType(Object value, Root<T> root, String key)
```

## Its Job

It converts generic filter criteria into JPA predicates.

Example:

```text
status = AWAITING_ALLOCATION
```

becomes a Criteria API predicate:

```text
criteriaBuilder.equal(root.get("status"), "AWAITING_ALLOCATION")
```

Example:

```text
brand contains "Jag"
```

becomes:

```text
criteriaBuilder.like(root.get("brand"), "%Jag%")
```

Example:

```text
createdDate >= 2024-01-01
```

becomes:

```text
criteriaBuilder.greaterThanOrEqualTo(root.get("createdDate"), parsedDate)
```

## Type Conversion

The method:

```text
getValueAsPerDataType(...)
```

is important because frontend sends values as strings or generic JSON values.

The backend must convert them to the correct Java type:

- String
- Integer
- Long
- Boolean
- Enum
- LocalDate
- LocalDateTime
- BigDecimal

For example:

```text
"2024-01-01" -> LocalDate
"123" -> Integer
"true" -> Boolean
"AWAITING_ALLOCATION" -> OrderStatus enum
```

## AND / OR Support

`createSpecification(..., andClause)` probably supports combining filters as:

```text
condition1 AND condition2 AND condition3
```

or:

```text
condition1 OR condition2 OR condition3
```

That is what made it support complex multi-condition admin queries.

## Q4. How did you convert filters into database queries?

### Answer

---

## Q5. Why use JPA Specifications?

### Answer

JPA Specifications are good for dynamic queries because you can build predicates at runtime. They avoid hardcoding every filter combination and integrate well with Spring Data JPA and Criteria API.

---

## Q6. How did sorting work?

### Answer

The frontend sent sorting fields and direction as `SortCriteria`. `SortingUtil` converted that into a Spring Data `Sort`, which was applied to the query.

---

## Q7. How did pagination work?

### Answer

The frontend sent page number and page size. `PaginationUtil` created a `Pageable`, and the repository applied limit/offset behavior so only one page of records was returned.

---

## Q8. How did you handle different data types?

### Answer

The utility method `getValueAsPerDataType` inspected the entity field type and converted incoming values accordingly. This was needed because filter values often arrive as strings but the entity field could be a date, number, boolean, enum, or string.

---

## Q9. What happens if the user filters by an invalid field?

### Strong Answer

Ideally, we validate the requested field names against allowed filterable fields for the entity. If the field is invalid, the API should return a bad request instead of attempting to build a query. This prevents runtime errors and avoids exposing internal entity structure.

If asked what current system did, you can say:

> The framework had to resolve field names dynamically, so invalid fields would need to be handled either through validation or exception handling. A good improvement would be to maintain an allowlist of filterable fields per screen/entity.

Yes. It was implemented as a generic repository abstraction. That made the same filtering framework reusable across different order screens.

Native SQL would work for fixed queries, but it becomes hard to maintain for many dynamic combinations. JPA Specifications allowed us to construct queries dynamically in a type-aware and reusable way. Native SQL could still be used for very complex or performance-critical queries.

# 21. Optimization Questions

Interviewers may ask how you would optimize these APIs.

---

## Q13. How would you optimize dynamic filtering APIs?

### Answer

I would optimize them at multiple layers:

1. **Database indexes**
   Add indexes on frequently filtered fields like:
   - status
   - vehicle order ID
   - common order number
   - VIN
   - CDS ID
   - brand/model/derivative
   - created date
   - order confirmed date

2. **Pagination**
   Always paginate results and avoid returning large datasets.

3. **DTO projections**
   Return only fields needed by the UI instead of full entity graphs.

4. **Query monitoring**
   Log slow queries and analyze execution plans.

5. **Restrict filterable fields**
   Use allowlists to avoid inefficient or unsafe filters.

6. **Avoid leading wildcard searches**
   `%value%` LIKE queries are expensive. Prefer prefix search where possible or use full-text search.

7. **Caching reference data**
   Cache static lookup data like brand, model, derivative.

8. **Use read replicas**
   For heavy reporting/list screens, route read queries to read replicas if architecture supports it.

## Q15. How would you optimize searches by employee name?

### Answer

Name searches using `LIKE %value%` can be expensive. Options:

1. Add indexes on normalized first and last name fields.
2. Use prefix search instead of contains search.
3. Store lowercase normalized columns for case-insensitive search.
4. Use database full-text search.
5. Use Elasticsearch/OpenSearch for advanced search if the use case becomes complex.

---

## Q16. How would you handle very large datasets?

### Answer

For very large datasets:

1. Use server-side pagination.
2. Avoid offset pagination for deep pages; consider keyset/cursor pagination.
3. Use DTO projections.
4. Add proper indexes.
5. Move complex reporting searches to read replicas.
6. Consider Elasticsearch/OpenSearch for complex search.
7. Add async export for large result sets instead of returning everything through API.

---

## Q17. Offset pagination vs cursor pagination — which is better?

### Answer

Offset pagination is simple and works well for normal admin tables. But for very large datasets or deep pages, offset becomes slower because the database still scans/skips many rows.

Cursor pagination is better when:

- dataset is very large
- users scroll deep into results
- there is a stable sort key like created date or ID

For admin grids with page numbers, offset is often acceptable initially, but cursor pagination is better for scale.

## Q19. How would you improve API response time?

### Answer

I would:

1. Use DTO projections instead of full entities.
2. Reduce joins where possible.
3. Add database indexes.
4. Cache static lookup data.
5. Use efficient count queries.
6. Use read replicas.
7. Avoid N+1 queries.
8. Compress responses if payloads are large.
9. Return only visible columns needed by the UI.

---

## Q20. How do you handle count queries in pagination?

### Answer

Pagination usually needs total count for total pages. Count queries can become expensive on large filtered datasets. To optimize:

1. Use simpler count queries.
2. Avoid unnecessary joins in count query.
3. Cache counts for common filters if acceptable.
4. For infinite scroll, avoid total count and use `hasNext`.
5. Use estimated counts for very large datasets if exact count is not required.

# 22. Potential Design Criticism and Good Response

## Q. Dynamic filtering can expose internal entity fields. How did you handle that?

### Good Answer

That is a valid concern. The safest approach is to maintain an allowlist of filterable fields per screen or entity. The frontend configuration can map display column names to backend-safe field names. The backend should reject any field not in the allowlist. That prevents users from filtering sensitive or internal fields and also protects performance by only allowing indexed/searchable fields.

---

## Q. Would you use this same design today?

### Good Answer

For admin grids and moderately complex filtering, yes, JPA Specifications are a good fit. If search requirements became more advanced — fuzzy search, full-text search, cross-entity search, very large data volumes — I would consider adding Elasticsearch/OpenSearch or database-specific full-text search. But for structured fleet/order data with filters and sorting, this design is practical and maintainable.
