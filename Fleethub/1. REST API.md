# 1. What Does “Vehicle Order Lifecycle” Mean Here?

In this application, a **vehicle order lifecycle** means the full journey of an MCP vehicle order from the time a user/employee requests or creates an order until the vehicle is allocated, modified if required, eventually handed over or returned, and tracked through history.

The lifecycle includes:

```text
Order Creation
   ↓
Validation
   ↓
Status Calculation
   ↓
Persist Order Details
   ↓
Allocation / Awaiting Allocation
   ↓
Order Modification
   ↓
Vista / SAP / operational updates
   ↓
Vehicle Handover
   ↓
Vehicle Return
   ↓
History / Audit Trail
```

Your resume point focuses mainly on:

1. **Creation**
2. **Allocation**
3. **Modification**
4. **Return**

These are exposed through REST APIs in `mcp-vehicle-order`.

CDS ID is the preferred unique identifier, but in some flows CDS ID may be missing, changed, or not reliable for imported/manual data. So first name and last name provided an additional fallback check to prevent duplicate active orders.

The modify API fetched the existing order, validated that the current status allowed updates, checked whether user identity fields changed, prevented duplicate active orders for the changed user, recalculated status using the current and updated order data, persisted changes, and created order history.

## Q9. How was order status calculated?

### Answer

Status was calculated in `CalculateOrderStatusService`. It had separate methods for create, update, upload, spare order, and sales report flows. Status depended on fields like VIN, common order number, build period, CI code, actual handover date, actual return date, and the current order state.

## Q10. Why did you centralize status calculation?

Because status could be changed by many flows — create, update, upload, allocation, Vista, SAP, sales report, return, and cancellation. Centralizing it avoided inconsistent business logic across APIs and made status rules easier to test.

# 19. Possible Deep Follow-Up Questions

## Q1. If two users create an order for the same employee at the same time, how would you prevent duplicates?

### Strong Answer

Application-level validation helps, but concurrent requests can still race. Ideally, we should also add database-level constraints or use transaction isolation/locking. Another improvement would be idempotency keys for order creation and optimistic locking for updates.

---

## Q2. What if the return API updates the order but the vehicle history API call fails?

### Strong Answer

That is a distributed consistency issue. In the current synchronous design, we would handle errors and potentially roll back the local transaction or return an error. A better design would be to use an outbox/event-driven approach where the order return event is persisted and retried asynchronously until vehicle history is updated.

---

## Q3. How would you improve order status calculation?

### Strong Answer

If status rules become more complex, I would consider using a formal state machine pattern. That would define allowed transitions explicitly and make it easier to reason about lifecycle movement from one status to another.

---

## Q4. How would you secure these APIs?

The service used OAuth2 resource server security and JWT validation. The JWT was converted into Spring Security authentication using `JwtConverter`. For more granular control, I would add method-level authorization using `@PreAuthorize` or route-level authorization based on RBAC permissions.
