# 4. Cookie-Based JWT Session Management

## What It Means

Cookie-based JWT session management means the authentication token is stored in a browser cookie instead of local storage.

The cookie may be:

```text
HttpOnly
Secure
SameSite=Lax/Strict/None depending on deployment
```

A common secure setup:

```text
Set-Cookie: access_token=<jwt>; HttpOnly; Secure; SameSite=Lax; Path=/
```

If the cookie is `HttpOnly`, frontend JavaScript cannot directly read it. That is good for security because it reduces token theft through XSS.

Instead, API calls automatically include the cookie when configured with credentials.

---

## Frontend Auth Flow

```text
1. User opens the app.

2. App checks current session by calling something like:
   GET /auth/me
   or
   GET /user

3. Browser automatically sends JWT cookie.

4. Backend validates JWT.

5. Backend returns user details and claims.

6. Frontend stores user session in React Context.

7. If valid:
   render protected app.

8. If invalid:
   redirect to login.
```

---

## Why Cookie-Based JWT Is Better Than localStorage

You can say:

> We preferred cookie-based JWT handling because tokens in localStorage are more exposed to XSS. With HttpOnly secure cookies, JavaScript cannot directly access the token, and the browser automatically sends it with API requests. This made session handling safer and simpler from the frontend side.

# 6. Role-Aware UI Rendering

## What It Means

Role-aware rendering means the UI changes based on the logged-in user’s permissions.

For example:

An admin user may see:

```text
Dashboard
Order Management
User Management
Role Management
Pricing Matrix
SAP Reports
Vista Reports
```

A fleet operations user may see only:

```text
Dashboard
Order Management
Allocation
Spare List
```

A finance user may see:

```text
Loan Agreement
Annual Statement
Finance Reports
```

---

## RBAC Flow

```text
1. User logs in.

2. Frontend fetches user details.

3. Frontend calls admin/RBAC API for authorization codes.

4. Response contains permissions like:
   ORDER_VIEW
   ORDER_CREATE
   ORDER_UPDATE
   ORDER_CANCEL
   ORDER_RETURN
   DASHBOARD_VIEW
   ROLE_MANAGEMENT_VIEW

5. Frontend stores these codes in context.

6. Sidebar filters menu items.

7. Page guard checks whether route is allowed.

8. Buttons/actions are conditionally rendered.
```

---

## Sidebar Filtering

Conceptual flow:

```text
sidebarItems = [
  { label: "Dashboard", route: "/dashboard", authCode: "DASHBOARD_VIEW" },
  { label: "Orders", route: "/mcpOrderList", authCode: "ORDER_VIEW" },
  { label: "Create Order", route: "/mcpOrder", authCode: "ORDER_CREATE" },
  { label: "Role Management", route: "/roleManagement", authCode: "ROLE_VIEW" }
]

userAuthCodes = ["DASHBOARD_VIEW", "ORDER_VIEW"]

visibleItems = sidebarItems.filter(item =>
  userAuthCodes.includes(item.authCode)
)
```

Result:

```text
Dashboard
Orders
```

The user does not see Create Order or Role Management.

# 16. Follow-Up / Cross Questions and Answers

## Q1. Why use React Context?

### Answer

React Context is useful for global state that many components need, such as authenticated user, permissions, sidebar state, theme, snackbar, and breadcrumbs. It avoids prop drilling and keeps shared app-level state centralized.

For frequently changing local UI state, I would still use component state or a dedicated state library. But for auth and permissions, Context is a good fit.

---

## Q2. Why use cookie-based JWT instead of localStorage?

### Answer

Storing JWT in localStorage exposes it to JavaScript, so if there is an XSS vulnerability, an attacker can steal the token. With an HttpOnly secure cookie, JavaScript cannot directly read the token. The browser sends it automatically with API calls. This improves security.

---

## Q3. How do you prevent CSRF with cookie-based JWT?

### Answer

Because cookies are automatically sent, CSRF must be considered. Mitigations include:

- `SameSite=Lax` or `SameSite=Strict`
- CSRF token for state-changing requests
- checking Origin/Referer headers
- using secure CORS configuration
- requiring Authorization headers for sensitive APIs if applicable

---

## Q4. How does role-aware rendering work?

### Answer

The user’s authorization codes are loaded after login and stored in context. Routes, sidebar items, and buttons are mapped to required permission codes. Components check whether the user has the required code before rendering. For example, the Return Vehicle button only appears if the user has `ORDER_RETURN`.

---

## Q5. Is frontend role-aware rendering enough for security?

### Answer

No. Frontend role-aware rendering improves UX but is not sufficient for security. Backend APIs must also enforce authorization because users can call APIs directly. The frontend hides unauthorized actions, while the backend validates JWT and permission before executing protected operations.

---

## Q6. How did you handle loading states?

### Answer

For data-heavy views, we showed skeleton loaders instead of blank screens. For tables, we rendered skeleton rows. For dashboard cards, we rendered skeleton cards. Buttons showed loading indicators during submissions to prevent duplicate actions.

---

## Q7. How did you handle errors?

### Answer

API errors were normalized into user-friendly messages. Pages displayed error alerts with retry options. For authentication errors like 401, users were redirected to login. For 403, users were shown an unauthorized page or access-denied message.

---

## Q8. How did you handle empty data?

### Answer

If an API returned an empty list, the UI showed an empty state instead of a blank table. For example: “No orders found. Try changing your filters.” Some empty states also included actions like “Clear filters” or “Create order” depending on permissions.

---

## Q9. Why use shadcn/ui?

### Answer

shadcn/ui provides accessible, composable UI primitives built on Radix and Tailwind. It gives flexibility because components live in the codebase and can be customized. For an internal admin application, it works well for consistent cards, tables, dialogs, dropdowns, alerts, badges, and skeleton states.

---

## Q10. How would you build the vehicle status dashboard?

### Answer

I would create reusable dashboard card components for key metrics like total orders, awaiting allocation, ready to handover, returned, cancelled, and spare vehicles. I would fetch dashboard summary APIs on page load, show skeletons while loading, render cards and charts on success, show empty state when there is no data, and show error state with retry on failure.

---

## Q11. How did dashboard data come from the backend?

### Answer

Dashboard APIs would return aggregated data such as order counts by status, monthly order counts, and spare order counts. The frontend would call these APIs, transform the response into chart/card data, and render the dashboard using cards and chart components.

---

## Q12. How do you optimize dashboard performance?

### Answer

I would:

- combine related dashboard metrics into fewer API calls
- cache dashboard responses for a short time
- use server-side aggregation in backend/database
- avoid fetching full order lists for summary counts
- lazy-load heavy charts
- use skeletons to improve perceived performance
- memoize expensive client-side transformations

---

## Q13. How do you optimize order tables?

### Answer

Use server-side pagination, filtering, and sorting. Avoid loading all orders into the browser. Return only columns needed for the table. Debounce search inputs. Use stable keys and memoized row rendering. For large datasets, consider virtualization.

---

## Q14. Why not store all order data in frontend state?

### Answer

Fleet order data can be large and frequently changing. Storing everything in the frontend would increase memory usage and create stale data issues. It is better to fetch paginated/filterable data from the backend and keep only the current view in frontend state.

---

## Q15. How do you handle token expiry?

### Answer

When an API returns 401, the auth context marks the session as unauthenticated and redirects the user to login. If refresh tokens are supported, the frontend can call a refresh endpoint first, then retry the original request. If refresh fails, redirect to login.

---

## Q16. How would you test role-aware UI?

### Answer

I would test:

- sidebar shows correct items for each role

- buttons are hidden when permissions are missing
- 401 redirects to login
- 403 shows unauthorized page
- loading/error/empty states render correctly
- action dialogs only open for authorized users

## Q17. What is the difference between 401 and 403?

### Answer

`401 Unauthorized` means the user is not authenticated or the session is invalid. `403 Forbidden` means the user is authenticated but does not have permission to access the resource or perform the action.

---

## Q18. How would you structure reusable loading/error/empty handling?

### Answer

I would create a reusable async state wrapper or pattern. Every data-driven component would check:

```text
if loading -> show skeleton
else if error -> show error alert
else if data empty -> show empty state
else -> show data
```

This ensures consistent behavior across order lists, dashboards, reports, and admin screens.

---

## Q19. How would you handle unauthorized direct URL access?

### Answer

Protected route logic checks whether the user is authenticated and has the required permission for that route. If not authenticated, redirect to login. If authenticated but unauthorized, redirect to unauthorized page.

- adding unit tests for permission helpers
