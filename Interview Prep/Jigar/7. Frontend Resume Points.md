---


---

# 2. Frontend SSO Flow

The frontend does not collect username/password.

Flow:

```text
User opens app
   ↓
AuthContext checks current session
   ↓
No session → show login page
   ↓
User clicks Login with SSO
   ↓
Browser redirects to backend auth/SSO endpoint
   ↓
ADFS login happens
   ↓
Backend sets secure JWT cookie/session
   ↓
User returns to frontend
   ↓
Frontend calls /me and /permissions
   ↓
App loads protected routes
```

---

# 3. Cookie-Based JWT Session

JWT/access token is stored in secure cookie.

Frontend API client uses:

```text
credentials: "include"
```

So browser sends cookie automatically.

Advantages:

```text
frontend does not manually store token in localStorage
HttpOnly cookie reduces token theft risk
centralized session handling
```

---

# 4. AuthContext

AuthContext manages authentication state.

It stores:

```text
user
isAuthenticated
loading
error
login()
logout()
refreshUser()
```

Typical app startup:

```text
AuthProvider mounts
   ↓
calls /me
   ↓
if success → user authenticated
   ↓
if 401 → redirect login
```

---

# 5. PermissionContext

PermissionContext manages authorization codes.

It stores:

```text
permissions
hasPermission(permission)
hasAnyPermission(list)
hasAllPermissions(list)
```

Flow:

```text
after user authenticated
   ↓
call /permissions
   ↓
store permission codes
   ↓
UI renders based on permissions
```

Example permissions:

```text
VIEW_ORDER
CREATE_ORDER
MODIFY_ORDER
RETURN_VEHICLE
CANCEL_ORDER
VIEW_DASHBOARD
MANAGE_USERS
```

---

# 6. Protected Routes

Protected route checks:

```text
Is user authenticated?
Does user have required permission?
```

Flow:

```text
If auth loading → show loader
If not authenticated → redirect login
If authenticated but no permission → unauthorized page
Else → render page
```

Example:

```text
<ProtectedRoute permission="VIEW_ORDER">
  <OrderListPage />
</ProtectedRoute>
```

---

# 7. Sidebar Visibility

Sidebar items are mapped to permissions.

Example:

```text
Dashboard → VIEW_DASHBOARD
Orders → VIEW_ORDER
Create Order → CREATE_ORDER
Allocation → VIEW_ALLOCATION
User Management → MANAGE_USERS
Role Management → MANAGE_ROLES
```

The UI filters menu items:

```text
visibleItems = items.filter(item => hasPermission(item.permission))
```

So users only see allowed navigation.

---

# 8. Action-Level Permissions

Buttons/actions are also permission-controlled.

Examples:

```text
CREATE_ORDER → show Create button
MODIFY_ORDER → show Edit action
CANCEL_ORDER → show Cancel action
RETURN_VEHICLE → show Return Vehicle action
DOWNLOAD_REPORT → show Download button
```

Pattern:

```text
{hasPermission("RETURN_VEHICLE") && <ReturnButton />}
```

or:

```text
<PermissionGuard permission="RETURN_VEHICLE">
  <ReturnButton />
</PermissionGuard>
```

# 11. Challenges Faced

## Challenge 1: Auth state during app load

UI should not flicker between login and app.

Solution:

> Auth loading state before rendering protected routes.

---

## Challenge 2: Permissions loaded after user

Permissions depend on authenticated user.

Solution:

> Load permissions after /me succeeds.

---

## Challenge 3: Consistent access checks

Avoid scattered permission logic.

Solution:

> Use `PermissionContext` and reusable `PermissionGuard`.

---

## Challenge 4: Session expiry

API may return 401 at any time.

Solution:

> Central API client handles 401 globally and redirects to login.

---

## Challenge 5: UI-only security limitation

Frontend hiding is not enough.

Solution:

> Backend also validates JWT and permissions.

---

## Interview Summary

> I implemented role-aware rendering by storing authenticated user and permissions in React Context. After SSO login, the frontend called user and permission APIs, stored authorization codes, and used them to protect routes, filter sidebar items, and show/hide buttons. The API client handled cookie-based JWT sessions with credentials included and standardized 401/403 behavior. I also standardized loading, error, and empty states across pages.
