# Vehicle Order Lifecycle — FastAPI + Python Explanation

This is how you can explain the **order lifecycle feature** as if it was built using **Python FastAPI**.

The order lifecycle means managing a vehicle order from:

```text
creation → validation → allocation → modification → cancellation → return → history
```

A good memory hook:

```text
CREATE → VALIDATE → STATUS → ALLOCATE → UPDATE → RETURN → HISTORY
```

---

# 1. What the Order Lifecycle Does

The order lifecycle manages the complete journey of a vehicle order.

It handles:

- creating a new vehicle order
- validating employee and vehicle details
- preventing duplicate active orders
- calculating order status
- allocating a vehicle/order
- modifying order details
- cancelling an order
- returning a vehicle
- maintaining audit history
- supporting filtered order lists

In simple words:

> The order service is the workflow engine for vehicle orders.

# 3. API 1 — Create Order

## Endpoint

```text
POST /orders
```

## Purpose

Creates a new vehicle order.

## Request contains

The request body contains:

```text
employee details
vehicle details
finance details
selected options
dealer-fitted accessories
required dates
pickup/drop details
```

Example business fields:

```text
cds_id
employee_name
payroll_number
brand
model
derivative
exterior_colour
interior_colour
loan_value
monthly_deduction
options
accessories
required_by_date
```

---

## FastAPI flow

```text
React form submits order
   ↓
FastAPI router receives request
   ↓
Pydantic schema validates request shape
   ↓
Auth dependency validates JWT
   ↓
Permission dependency checks CREATE_ORDER
   ↓
Order service runs business validations
   ↓
Status service calculates initial status
   ↓
SQLAlchemy transaction saves records
   ↓
History record is created
   ↓
Response returned
```

---

## Business validations

Before saving, the service checks:

### 1. Employee validation

```text
Is CDS ID valid?
Is payroll number present?
Are employee details complete?
```

### 2. Duplicate active order validation

```text
Does this employee already have an active order?
```

Check could be by:

```text
cds_id
or first_name + last_name
```

### 3. Vehicle availability validation

```text
Is this vehicle/common order number already assigned or reserved?
```

---

## What gets saved

Creating an order may save data into multiple tables:

```text
vehicle_orders
order_user_details
order_finance_details
order_options
dealer_fitted_accessories
order_workflow_activity
order_history
```

---

## Interview explanation

> The create order API accepted a full order request, validated the employee and vehicle information, checked for duplicate active orders, calculated the initial status, saved related order records in a transaction, and created a history entry.

# 6. API 4 — Modify Order

## Endpoint

```text
PUT /orders/{order_id}
```

## Purpose

Updates an existing vehicle order.

---

## FastAPI flow

```text
Request received
   ↓
Pydantic validates payload
   ↓
JWT + MODIFY_ORDER permission checked
   ↓
Fetch current order
   ↓
Check if current status allows modification
   ↓
Check if employee details changed
   ↓
If employee changed, check duplicate active order
   ↓
Recalculate status
   ↓
Update records in transaction
   ↓
Create history
   ↓
Return updated order
```

---

## Update-specific validations

### 1. Status validation

Some statuses should not be freely updated:

```text
CANCELLED
RETURNED
OFF_LEASE
```

### 2. Employee change validation

If the order is reassigned to another employee:

```text
Check whether new employee already has active order
```

### 3. Important field changes

For example:

```text
CI code changed
vehicle configuration changed
common order number changed
```

These may affect status.

---

## Interview explanation

> The update API was more complex than create because it compared the existing order with the incoming request. It validated whether the current status allowed updates, handled employee-change scenarios, recalculated status, updated records, and created history.

# 13. Order Status Calculation

Status is central to the lifecycle.

Possible statuses:

```text
AWAITING_ALLOCATION
SUBMIT_TO_BUILD
READY_TO_HANDOVER
WITH_CUSTOMER
CANCELLED
RETURNED
```

Status depends on:

```text
VIN present
common order number present
build period present
CI code change
handover date
return date
current status
```

---

## Why separate status service?

Because status can change from many flows:

```text
create
update
allocation
upload
cancel
return
external file updates
```

So a separate `OrderStatusService` keeps logic consistent.

# 15. Database Transaction

For create/update/return flows, use transaction boundaries.

Example create order transaction:

```text
begin transaction
   save order
   save user details
   save finance
   save options
   save accessories
   save history
commit
```

If something fails:

```text
rollback
```

This prevents partial order creation.


---

Use database filtering, not frontend filtering.

Why?

```text
large datasets
fresh data
better indexed search
less network payload
```

## For create/update

Use transactions and avoid unnecessary downstream calls.
