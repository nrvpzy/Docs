# 4. Create Order API

## Endpoint

```text
POST /orders
```

## What it does

Creates a new vehicle order.

Request contains:

```text
employee details
vehicle details
finance details
selected options
dealer-fitted accessories
required dates
pickup/drop details
```

---

## FastAPI flow

```text
React submits order form
   ↓
FastAPI route receives request
   ↓
Pydantic validates request shape
   ↓
JWT dependency validates logged-in user
   ↓
Permission dependency checks CREATE_ORDER
   ↓
Service validates business rules
   ↓
Status is calculated
   ↓
SQLAlchemy saves records in transaction
   ↓
Order history is created
   ↓
Response returned
```

---

## Business validations

### Employee validation

Checks:

```text
CDS ID exists
payroll number exists
employee fields are complete
```

### Duplicate active order validation

Checks:

```text
Does this employee already have an active order?
```

Usually based on:

```text
cds_id
or first_name + last_name
```

### Vehicle availability validation

Checks:

```text
Is selected vehicle/common order number already used or reserved?
```

---

## Database records saved

A single order may save into multiple tables:

```text
orders
order_user_details
order_finance_details
order_options
dealer_fitted_accessories
order_workflow_activity
order_history
```

This is wrapped in a transaction.

If one save fails:

```text
rollback everything
```

---

## Pydantic schema example conceptually

```text
OrderCreateRequest:
  user_details
  vehicle_details
  finance_details
  options
  accessories
```

Pydantic validates structure and basic types.

Business validation happens in service layer.

# 10. Challenges Faced

## Challenge 1: Status complexity

An order status could change from multiple workflows:

```text

return

```

Solution:

> Created a centralized status service to calculate status consistently.

---

## Challenge 2: Duplicate active orders

Same employee could accidentally get multiple active orders.

Solution:

> Added duplicate validation based on CDS ID and name against active statuses.

> Used SQLAlchemy transactions to ensure either all records are saved or none are.

## Challenge 4: Cross-service dependency

Return flow required vehicle history update in vehicle-data-service.

Solution:

> Used service-to-service calls with error handling, timeout, and transaction boundary awareness.

# Resume Point 2

> **Built a reusable dynamic filtering, sorting, and pagination system using FastAPI, SQLAlchemy, and Pydantic schemas, enabling admins to execute complex multi-condition searches across fleet order data and reducing query resolution time by over 30%.**

---

# 1. What This Means

Admins and operations users needed to search large order datasets.

They wanted filters like:

```text
status = AWAITING_ALLOCATION
brand = Jaguar
created_date between dates
CDS ID = xyz
VIN contains abc
derivative = PHEV
```

Instead of building many separate APIs, you built a generic filter system.

---

# 2. Problem Before This

Without dynamic filtering, you would need endpoints like:

```text
/orders/by-status
/orders/by-brand
/orders/by-status-and-brand
/orders/by-date-range
/orders/by-employee
```

This does not scale.

So the solution was:

```text
one generic API + dynamic filters
```

---

# 3. API Design

Endpoint:

```text
GET /orders
```

or

```text
POST /orders/search
```

Request/query criteria:

```json
{
  "filters": [
    {"field": "status", "operator": "eq", "value": "AWAITING_ALLOCATION"},
    {"field": "brand", "operator": "eq", "value": "JAGUAR"},
    {"field": "created_at", "operator": "gte", "value": "2024-01-01"}
  ],
  "sort": [
    {"field": "created_at", "direction": "desc"}
  ],
  "page": 1,
  "page_size": 25
}
```

---

# 4. Pydantic Schemas

You define schemas like:

```text
FilterCondition
  field
  operator
  value

SortCondition
  field
  direction

SearchRequest
  filters
  sort
  page
  page_size
```

Pydantic validates:

```text
field exists
operator is allowed
page_size is within max limit
sort direction is asc/desc
```

---

# 5. SQLAlchemy Query Building

The backend converts filter conditions into SQLAlchemy expressions.

Examples:

```text
eq       → Model.field == value
neq      → Model.field != value
like     → Model.field.ilike("%value%")
gte      → Model.field >= value
lte      → Model.field <= value
in       → Model.field.in_(values)
between  → Model.field.between(start, end)
```

---

# 6. Pagination

Pagination uses:

```text
LIMIT
OFFSET
```

Example:

```text
page = 2
page_size = 25
offset = (page - 1) * page_size
```

Query:

```text
query.limit(page_size).offset(offset)
```

---

# 7. Sorting

Sorting uses:

```text
ORDER BY created_at DESC
ORDER BY status ASC
```

Multiple sort fields can be supported.

---

# 8. Response

```json
{
  "items": [],
  "page": 1,
  "page_size": 25,
  "total": 250,
  "total_pages": 10
}
```

This lets frontend render pagination controls.

---

# 9. Reusability

The same filtering framework can be reused across:

```text

SAP reports
Vista reports

finance reports

```

Only the allowed fields mapping changes per entity.

# 10. Security / Safety

A key challenge is not allowing arbitrary DB fields.

Solution:

```text
field allowlist
```

Example:

```text
allowed_order_filters = {
  "status": Order.status,
  "brand": Order.brand,
  "cds_id": Order.cds_id,
  "vin": Order.vin,
  "created_at": Order.created_at
}
```

If frontend sends unknown field:

```text
400 Bad Request
```

---

# 11. Performance Optimizations

Used or recommended:

```text
database indexes
server-side pagination
DTO response schemas
max page size limit
avoid loading relationships unnecessarily
avoid leading wildcard when possible
slow query monitoring
```

Indexes on:

```text

cds_id
vin
common_order_no
created_at
brand

```

---

# 12. Why Not Cache Everything?

Because order data is transactional and changes often.

Caching all filter combinations is impractical.

Better approach:

```text
server-side filtering + indexes
```

Cache only stable reference data:

```text
brands
models
derivatives
colors
permissions metadata
```

```text
Who is the user?
```

## Authorization

# 3. SSO Flow

```text
User opens React app
   ↓
No valid session
   ↓
User clicks Login with SSO
   ↓
Browser redirects to ADFS
   ↓
ADFS authenticates user
   ↓
ADFS redirects back with authorization code
   ↓
Auth service exchanges code for tokens
   ↓
Receives access token + ID token
   ↓
JWT stored in secure cookie
   ↓

```

Common dependency:


```text
   ↓

```

```text

```

# 12. Why Separate Admin/RBAC Service?

Because ADFS authenticates enterprise identity, but app permissions are domain-specific.

ADFS says:

```text
This is John.
```

RBAC service says:

```text
John can return vehicles but cannot manage users.
```

This avoids managing hundreds of app-specific permissions inside ADFS.

# 13. Challenges Faced

## Challenge 1: Token validation across microservices

Each service had to validate JWT consistently.

Solution:

> Shared auth dependency pattern or common auth utility.

---

## Challenge 2: Fine-grained permissions

Different actions needed different permissions.

Solution:

> Permission-based dependencies and frontend guards.

---

## Challenge 3: Avoid calling RBAC service on every request

Calling admin service every time is slow.

Solution options:

```text
cache permissions
include coarse roles in JWT
fetch permissions after login
short-lived permission cache
```

---

## Challenge 4: 401 vs 403 handling

Clear difference:

```text
401 = not logged in / invalid token
403 = logged in but no permission
```

---

## Challenge 5: Secure cookie concerns

JWT in cookie improves XSS protection if HttpOnly, but CSRF must be handled.

Mitigations:

```text
SameSite cookies
CSRF token for unsafe methods
CORS restrictions
Origin checks
```

# 14. Interview Summary

> I implemented enterprise SSO using OAuth2/OIDC with ADFS. After login, the auth service exchanged the authorization code for tokens and stored the JWT in a secure cookie. For authorization, we implemented RBAC with users, roles, and permissions. Endpoints were protected using permission-based dependencies, and the React frontend used the same permissions to control routes and buttons.
